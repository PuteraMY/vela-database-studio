## P1B-2A index read path

- Verified local/remote P1B-1 head `77bfc1b264392cd5320ca5a52e413972570a2d6f`, parent P1A, and open PR #2 targeting P1A before branching. The new request supersedes the P1B-1 stop rule. Work alone; no new applicable verified skill, dependency, UI, planner or storage-algorithm change.
- `IndexReadPath` derives a per-table ID→current-row directory from existing P1B-1 identities once during candidate publication. It allocates no new row IDs and never scans row arrays for individual reads. Directory preparation and physical maintenance finish before rows/catalog/directories publish together; failure leaves all live read state intact. This adds O(total rows) directory construction to existing write/restore costs, not to each read.
- Frozen opaque table/index handles identify object lifetimes within one Database instance. Row references pair the existing numeric ID with its table handle. Handles survive ordinary DML, but DROP/recreation or logical restore invalidate previous lifetimes; index DROP/recreation invalidates its index handle. Cross-table batch resolution, foreign-database handles and copied/forged handles are rejected. Numeric IDs alone are not transferable identities. Handles remain internal to the Worker and are absent from logical exports.
- Exact lookup takes one value per declared index component and calls real B+tree search. Both maintenance and reads share BOOLEAN→0/1 and -0→0 normalization. NULL keys match physically; this is not SQL `= NULL`. Numbers/text are not coerced. Invalid arity, nonfinite values and keys exceeding the current tree slot fail explicitly; a valid absent key returns an empty list. UNIQUE enforcement remains P1B-1's responsibility.
- Bounds use P1A lexicographic ordering: one to all index components, inclusive by default, either direction. A short prefix is an ordinary shorter key, not a wildcard: upper `[1]` excludes stored `[1, ...]` keys. Bounds are copied/validated at cursor creation. Each pull resolves a current row and checks its key; no complete result list is materialized. Return, break, throw, exhaustion and errors close the physical iterator and release captured cursor state.
- Any successful DDL/DML publication (including a no-op or unrelated table change) invalidates open cursors before their next pull, including cursors not yet started. Reads and failed statements preserve them; successful logical restore invalidates cursors and handles. Closed cursors remain done. This conservative fail-fast policy is not MVCC/snapshot isolation. Existing row references remain live through normal UPDATE and fail after DELETE.
- Tests separate physical API reference-model checks from SQL/SQLite comparisons, instrument B+tree calls and prohibit table-array access during reads. Internal benchmark batches measure row resolution, exact lookup plus resolution, bounded cursor traversal and a reference array scan; they must never be described as SQL SELECT speedups. P1B-2B should begin with a single-table equality index operator and SQL binding/fallback differential tests; no optimizer work starts here.

## P1B-1 SQL index maintenance

- The later P1B-1 request supersedes the previous P1A stop instruction. Branch from verified `5f25dab28c73b7661268119d7f718d0f76965896`; target the P1A branch in a separate PR, leaving PR #1 and main unchanged. Work alone; no applicable verified skill is loaded and no dependencies are added.
- Keep P0 row objects and logical export format unchanged. A private per-table sidecar associates each row with a monotonically allocated unsigned ID starting at 1. UPDATE preserves IDs; DELETE never renumbers or reuses IDs; failed statements consume none. DROP/recreation and explicit logical restore start a new identity lifetime. Restore rebuilds all indexes before publishing; IDs are neither SQL columns nor durable handles. The Worker uses logical restore for CSV/generator replacement, which also starts this new lifetime.
- SQL keys use existing strict type validation and `normalize`: BOOLEAN becomes 0/1, -0 becomes +0, NULL stays NULL, numbers and text are not implicitly coerced. Ordering is NULL < finite NUMBER < TEXT, then lexicographic composite order and stable row ID for duplicates. Text uses case-sensitive UTF-16 code-unit order, matching P0 JavaScript comparisons (not every SQLite UTF-8 collation edge case). UNIQUE allows duplicate keys containing any NULL; existing candidate-state constraint validation remains authoritative. No new COLLATE/affinity syntax is introduced.
- Every explicit CREATE INDEX definition owns a real P1A B+tree. PRIMARY KEY and column UNIQUE constraints still use P0 validation and do not acquire implicit trees in this milestone. Repeated index columns retain P0 behavior, within the codec's 64-component limit. Map objects hold catalog/identity associations and temporary DML differences only, never the ordered index itself.
- Extend P0 statement atomicity: validate candidate rows, prepare detached affected trees, remove obsolete entries before adding changed entries, then publish rows/identities/catalog/trees together. Unchanged trees are shared privately; modified trees are copied through the validated P1A image boundary. CREATE populates existing rows; DROP removes the corresponding tree. Failed constraints, key encoding or page allocation publish nothing. This is memory-only statement atomicity, not a transaction or durability implementation.
- Default SQL indexes start with 4 KiB pages, 16 keys and 128-byte slots. Longer keys grow slot/page capacity by rebuilding a detached tree; pages remain fixed-size within each tree. At the 64 KiB page limit, fanout reduces to at least three keys. Maximum encoded composite key is 21,823 bytes; longer keys or more than 64 components fail atomically with a Malay diagnostic. Overflow records remain deferred. Optional fixed TreeOptions support bounded hosts and reproducible failure tests.
- Full internal validation compares every sorted expected key/ID pair with the tree and checks row identity, catalog membership, uniqueness and all P1A structural invariants. Diagnostic results are detached copies. SELECT, joins, EXPLAIN, UI and P1A storage algorithms stay unchanged. P1B-2 should begin with a read-only stable-ID resolver and exact-key index access contract plus differential tests before connecting planner choices; it is not started here.

## P1A storage boundary

- Work only on independent storage components, preserving SQL/catalog/EXPLAIN/UI behavior. No verified project-local skill directly applies: frontend-design concerns UI, and database/testing guides remain legacy; none is loaded for this engine milestone.
- Pages contain actual fixed-size byte arrays, not a Map-backed substitute index. A memory pager owns deterministic positive IDs and reuses the smallest released ID. Per-operation staged writes publish together; this is in-process failure atomicity, not SQL transactions or durability.
- Use bounded fixed slots and a configurable maximum encoded key size. Reject oversized keys before publication; overflow/variable-length records are deferred. A leaf stores composite key plus an unsigned 32-bit row reference. Internal separators are the exact minimum (key, row reference) of the right subtree.
- Physical keys use a total order independent of SQL predicates: NULL < BOOLEAN < finite NUMBER < TEXT; composite keys compare lexicographically, shorter prefixes first. Strings preserve UTF-16 code units; -0 normalizes to +0. Repeated keys have distinct row references; an identical pair is an idempotent no-op. SQL affinity, UNIQUE/NULL rules and stable row identities must be addressed explicitly before P1B integration.
- A tree owns its pager. Detached page images and a versioned root/configuration descriptor define a future persistence boundary without implementing disk/IndexedDB/WAL. A snapshot adapter may index exported table rows by their ordinal; it is not a live SQL index and must be rebuilt after row changes.
